2. RECONCILIATION: 12 REACHABLE FILES vs EARLIER LIST & search.py SET COUNT
--------------------------------------------------------------------------------
Reconciliation of Reachable Files:
  1. In earlier draft reports, an assistant hypothesized files named:
       `hybrid_search.py`, `lexical_search.py`, and `theme_indexer.py`.
  2. Repository verification proves:
     - `hybrid_search.py` and `lexical_search.py` DO NOT EXIST anywhere in the codebase.
       All search mechanisms (lexical, semantic fallback, hybrid reranking, CWPR precision)
       are implemented inside `backend/app/core/engine.py` (RizalEngine).
     - `theme_indexer.py` is located at `backend/scripts/theme_indexer.py` as an offline build tool.
       It is never imported or reachable from the FastAPI backend or search endpoint.
     - The 12 genuine reachable files from `app/api/v1/search.py` are the authentic modular dependencies:
       analyzer.py, config.py, engine.py, perf_instrumentation.py, query_counter.py,
       robust_aligner.py, sequence_aligner.py, tagalog_parser.py, tagalog_stemmer.py,
       database.py, suggestions.py, and search.py itself.

Explanation of Why search.py Showed '0 Sets' in an Earlier AST Query:
  1. In Python's `ast` module:
     - `ast.Set` matches ONLY Set Literals (e.g. `{'a', 'b'}`).
     - `ast.SetComp` matches ONLY Set Comprehensions (e.g. `{x for x in y}`).
     - `seen_ids = set()` is an `ast.Call` where `func.id == 'set'`, NOT an `ast.Set`.
  2. In `app/api/v1/search.py`, lines 64, 65, and 66 use `set()` constructor calls:
       seen_noli_ids = set()
       seen_elfili_ids = set()
       seen_precise_ids = set()
  3. An earlier AST script that searched strictly for `isinstance(node, ast.Set)` returned 0 for search.py,
     whereas `grep -c 'set('` returned 3. When `ast.Call` is correctly matched, both AST and grep return exactly 3.
