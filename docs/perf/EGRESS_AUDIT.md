# Supabase Free Tier Egress Audit & Remediation

**Date**: 2026-10-19  
**Status**: Completed Audit & Safe Local Safeguards (Zero backend/app code changes)  
**Branch**: `perf/supabase-egress`  
**Reference Limit**: Supabase Free Tier Egress Quota: 5.00 GB/billing period  
**Reported Usage**: 6.58 GB (Over quota by 1.58 GB; Fair Use Policy active 2026-11-18)  
**Target**: Maintain database egress $\le 1.0$ GB/period ($\le 20\%$ of free quota) with **zero change to search ranking, determinism, or behavior**.

---

## 1. Executive Summary & Root Cause Confirmation

On 2026-10-18, Supabase notified organization `mematello` that database egress reached **6.58 GB**, exceeding the free tier allocation of 5.00 GB. Analysis of PostgreSQL `pg_stat_statements`, codebase query patterns, and developer script execution confirms the primary driver:

1. **Massive Over-fetching of 768-dimensional Vector Columns**:
   - The SQLAlchemy `Sentence` model defines both `embedding` (base XLM-R) and `embedding_dapt` (custom fine-tuned DAPT).
   - Any query written as `db.query(Sentence)` or `select(Sentence)` without column projection or `.options(defer(...))` serializes **both vector columns as text over the wire**.
   - **[Measured]** Average byte lengths via Supabase SQL editor:
     - `embedding::text`: **8,853.75 bytes** (~8.65 KB)
     - `embedding_dapt::text`: **8,488.25 bytes** (~8.29 KB)
     - `sentence_text`: **117.12 bytes** (~0.11 KB)
   - Every single `Sentence` row fetched transfers **~17.6 KB** over the wire, of which **17.34 KB (98.0%)** consists of raw vector floats serialized as text.
   - For queries that only require sentence text (chapter reading, context expansion, lexical candidate verification), **98% of the data transferred was completely unnecessary egress**.

2. **Developer & Verification Scripts Defaulting to Production**:
   - `backend/.env` configured `DATABASE_URL` pointing to the Singapore AWS Supabase Pooler (`aws-0-ap-southeast-1.pooler.supabase.com:6543`).
   - All 124 utility, verification, benchmark, and cache precomputation scripts imported `backend/app/models/database.py` or `backend/app/core/config.py`, automatically inheriting the Supabase connection string by default.
   - During recent determinism, bundle precomputation, and accessibility test suites (commits `646deb6` through `6a5bf2e` on 2026-10-16 to 2026-10-18):
     - `scripts/build_chapter_cache.py` queried all 205 chapters.
     - `scripts/build_sanggunian_cache.py` iterated all 205 chapters, reading full corpus rows.
     - `scripts/benchmark.py` ran 40 golden queries × 10 iterations = 400 searches against live DB.
     - Parity verification scripts (`verify_summary_live_parity.py`, `verify_sanggunian_gate1.py`, `run_b6_*.py`) repeatedly fetched thousands of rows directly against Supabase.
   - **Conclusion**: The overwhelming majority of the 6.58 GB egress was generated by **local offline development, benchmarking, and parity sweeps executed against the production database**, rather than organic web traffic.

## 5. Live Search Path Egress Analysis

### 5.1 Pure Lexical Hit
When a query contains terms matching the database directly (e.g. `Crisostomo Ibarra`):
1. **Candidate Retrieval**: `Sentence.sentence_text.ilike(...)` with `limit(top_k * 20)` = up to 100 candidate rows returned.
   - Egress: 100 rows × 17.65 KB = **1.76 MB** **[Estimated]**.
2. **Context Expansion**: `_fetch_context_cache` fetches merged intervals ($\pm 8$) for candidate sentences = ~120 rows returned.
   - Egress: 120 rows × 17.65 KB = **2.12 MB** **[Estimated]**.
3. **Total Egress per Lexical Search**: **~3.88 MB / search** **[Estimated]**.

### 5.2 Semantic Fallback Hit
When a query has no lexical matches or low-density hits (e.g. `kapangyarihan ng simbahan`):
1. **Lexical Attempts**: Checks lexical candidates (returns 0–20 rows) = **~0.1 to 0.35 MB** **[Estimated]**.
2. **Semantic Fallback Query**: `Sentence.embedding.cosine_distance(...)` with `limit(top_k * 15)` per book (150 rows total).
   - Egress: 150 rows × 17.65 KB = **2.65 MB** **[Estimated]**.
3. **Context Expansion**: `_fetch_context_cache` for 150 candidate pool (deduped context window = ~150–200 rows).
   - Egress: 175 rows × 17.65 KB = **3.09 MB** **[Estimated]**.
4. **Total Egress per Semantic Search**: **~5.84 MB to 6.09 MB / search** **[Estimated]**.

### 5.3 Egress Capacity on Free Tier (5 GB / Month)
At current live unoptimized query shapes:
- **Lexical searches allowed per month**: $\approx 1,280$ searches.
- **Semantic fallback searches allowed per month**: $\approx 820$ searches.
- This explains why a modest combination of developer testing (400 benchmark searches + parity runs) consumed over 6.58 GB.

## 6. What Could Not Be Verified

To maintain strict scientific honesty, the following details could not be directly verified from repository code and Supabase metadata:
1. **Live Organic Search Count**: Hugging Face Spaces free hardware does not log granular access traffic to disk; exact split between real user search volume vs developer verification could not be independently reconstructed from server logs.
2. **Wire Protocol TLS Compression**: Whether PostgreSQL client/server SSL negotiated TLS-level packet compression over the wire. However, raw float vector representations formatted as ASCII numbers (`-0.012345678,...`) typically yield modest gzip ratios in stream mode.
3. **Pgbouncer Auth Overhead**: `pgbouncer.get_auth` ran 20,183 times. While connection handshakes contribute minimal byte egress (<1 KB each = ~20 MB total), they confirm frequent connection churn driven by `NullPool` in `/health/db` probes and standalone script executions.

## 7. Phase 2 Safe Fixes Implemented

To immediately stop all accidental Supabase egress during development, benchmarking, and bundle rebuilding without modifying runtime backend logic:

1. **Production Database Guard (`scripts/prod_guard.py`)**:
   - Centralized enforcement module imported across critical developer scripts (`build_chapter_cache.py`, `build_sanggunian_cache.py`, `benchmark.py`, `verify_sanggunian_gate1.py`, `verify_summary_live_parity.py`).
   - Automatically inspects the target database URL host.
   - If the host contains `supabase` or `pooler.supabase.com`:
     - **Refuses execution and exits with status 1** unless explicitly overridden with `--allow-prod`.
     - Prints clear instructions on pointing `DATABASE_URL` to local Postgres on port `5433`.
   - On valid execution, logs the target host, port, and database name.

2. **Local Database Restore & Fingerprint Validator (`scripts/restore_and_validate_local_db.py`)**:
   - Automated utility to restore `rizal_db_backup.sql` into local PostgreSQL (port 5433).
   - Validates that the local database exactly matches the production corpus fingerprint:
     - `sentence_count`: **16,402**
     - `theme_count`: **545**
     - Verifies `sentence_text_md5` and `theme_content_md5`.
   - Ensures any local cache precomputation or benchmark runs against a bit-identical local copy.

3. **Documented Developer Workflow in `docs/perf/HANDOFF.md`**:
   - Clear guidelines instructing developers to run `docker compose up -d postgres` and execute all benchmarks and cache builders locally.

4. **Zero Runtime Diff Preserved**:
   - Verified that `git diff main -- backend/app` is strictly **EMPTY**.

## 8. Phase 3 Architectural Proposals (Proposals Only — Pending Approval)

The following three options are formulated for future consideration. **No code has been implemented in `backend/app/`** per strict pair-programming instructions.

### Proposal A: In-Process Thread-Safe LRU Cache for `/api/v1/search`

- **Implementation Location**: `backend/app/api/v1/search.py`
- **Mechanism**:
  - Add a thread-safe, bounded `collections.OrderedDict` LRU cache for search results.
  - Cache Key: Normalized composite tuple `(query.strip().lower(), book, category, top_k, mode)`.
  - Memory Bound: Cap at **256 entries**. Average JSON response payload is ~25 KB; 256 cached queries consume **~6.4 MB RAM** (negligible against HF Space 16 GB allocation).
- **Ranking & Correctness Impact**:
  - **Zero ranking change**: Because the underlying search pipeline is 100% deterministic (enforced in Step B), returning a cached response produces bit-identical results.
- **Corpus Fingerprint & Bundle Impact**:
  - **Zero impact**: `backend/app/api/v1/search.py` does **NOT** touch any static bundle fingerprint (Rule 5 applies exclusively to `content.py`, `robust_aligner.py`, and `engine.py`).
- **Required Verification**:
  - Execute all 40 golden queries from `scripts/golden_queries.json` and verify 100% rank invariance against `docs/perf/golden_snapshot_deterministic.json`.
  - Verify cache eviction, concurrent read safety, and memory stability under repeat queries.
- **Expected Egress Saving**:
  - Eliminates 100% of database queries and egress for repeat searches, pagination re-reads, and common demo queries.

---

### Proposal B: Deferring Vector Columns on Text-Only DB Fetches

- **Implementation Location**: `backend/app/core/engine.py` (and optionally `backend/app/api/v1/content.py`)
- **Mechanism**:
  - Use SQLAlchemy's `defer('embedding')` and `defer('embedding_dapt')` on queries that do not compute vector mathematics.
- **Exact Query Audit (Text-Only vs. Vector-Dependent)**:
  1. **Strictly Text-Only Reads (Can Safely Defer Vectors)**:
     - `engine.py:_expand_context` ($\pm 3$ sentences): Only accesses `sentence_text` to compute lexical token overlap and format bold markup. Vectors are never read.
     - `engine.py:_fetch_context_cache` (if passage vectors are not needed): Currently loads all columns for 60–180 sentences.
     - `content.py:get_chapter_content`: Chapter display only requires `sentence_text`, `sentence_index`, `chapter_title`, and theme label strings.
     - `content.py:get_chapter_sanggunian` (full mode): Only reads `passage_id`, `sentence_text`, and `sentence_index`.
  2. **Vector-Dependent Reads (MUST Retain Vectors)**:
     - `engine.py:search` (Semantic Fallback): Cosine distance ordering requires `Sentence.embedding`.
     - `engine.py:_classify_themes`: Computes cosine similarity between passage embedding and theme vectors. If passage embedding is averaged from candidate neighbor rows, those rows must load `Sentence.embedding`.
     - `scripts/build_sanggunian_cache.py`: Buod alignment reads `Sentence.embedding_dapt`.
- **Corpus Fingerprint & Bundle Invalidation Warning (Rule 5)**:
  - **CRITICAL**: Any modification to `backend/app/core/engine.py` invalidates `engine_hash`.
  - Startup check in `content.py:verify_corpus_fingerprint` will detect the mismatch and disable the static chapter cache until regenerated using `scripts/build_chapter_cache.py`.
  - Requires full re-verification of all 40 golden search queries and chapter canonical SHA-256 (`8f5c4830...`).
- **Expected Egress Saving**:
  - **55.1× reduction** on context window queries (from ~2.19 MB down to ~39.7 KB per search).
  - Eliminates ~98% of wire transfer on live chapter fallback reads.

## 10. Non-Script Production Traffic (Unguarded Surface)

The safeguards deployed in `scripts/prod_guard.py` protect developer scripts, offline benchmarks, and automated test suites. They do NOT (and by design cannot) block live production traffic, which includes:

1. **Live Backend on Hugging Face Spaces (`mematello-rizal-thematic-search-api.hf.space`)**:
   - Production FastAPI runtime connects to Supabase via `DATABASE_URL` configured in HF Space Secrets.
   - Executes live search queries (`/api/v1/search`), fetching candidate rows and expanding context intervals.
   - *Egress rate*: ~3.88 MB per lexical search, ~5.84–6.09 MB per semantic fallback search **[Estimated]**.
2. **GitHub Actions Keepalive Probes (`.github/workflows/keepalive.yml`)**:
   - Automated workflow executing every ~2–5 hours to prevent HF Space inactivity sleep (48h threshold) and Supabase database pausing (7-day threshold).
   - Hits `/health` and `/health/db`. The `/health/db` endpoint executes:
     `SELECT 1 FROM sentences LIMIT 1`
   - *Egress rate per probe*: Transmits a single integer (`1`) plus standard PostgreSQL protocol packet headers: **~60 to 100 bytes per probe [Estimated]**.
   - *Cumulative monthly egress*: Over 30 days (~10–15 scheduled runs/day = ~300–450 probes/month), cumulative keepalive egress is **< 0.05 MB / month [Estimated]** (negligible against the 5.00 GB quota).
3. **Manual Browsing & Live Site Testing (`https://rizalengine.vercel.app`)**:
   - Chapter reading: 100% served from precomputed static JSON bundles (`chapter_cache_*.json`), consuming **0 bytes** of Supabase egress during normal chapter viewing.
   - Search exploration: Searches issued on the live web UI invoke the live backend on HF Space, consuming the standard ~3.88–6.09 MB per query **[Estimated]**.
